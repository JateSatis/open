# $implement — выполнить задачу от ветки до сдачи

Задача: сообщение с вызовом навыка или задача выше в переписке

Перед началом прочитай `AGENTS.md` и `CLAUDE.md`. Промпт — в переписке. Он написан навыком `$spec`: в нём решения
человека, где лежит код, пункты и критерии приёмки `К<пункт>.<n>`. Решения человека не
пересматривай. Подсказки — не приказ: нашёл путь лучше — иди им и напиши об этом в отчёте.
Код мог уйти вперёд с момента написания промпта — сверяйся с ним, а не с промптом.

Процесс — раздел 2 CLAUDE.md. Здесь — как именно его проходить.

## 1. Старт

1. Проверь `git status`, текущую ветку, дифф и историю. Посторонние правки не трогай
   и не коммить; при пересечении с задачей выясни, как их учитывать.
2. Новая задача — ветка из промпта от `master`. Продолжение начатой задачи —
   в её текущей ветке, сначала изучи сделанное и остаток ТЗ.
3. Сразу подними окружение в фоне: `node scripts/device.mjs up` через shell-сессию Codex (см. `AGENTS.md`). Он
   берёт подключённый телефон; вышел с кодом 4 — телефон не подключён: спроси человека
   (навык `device`, «Где проверять») и только по его ответу — `up --emulator`. Пока
   поднимается — читай код; к первой проверке устройство уже готово.
4. Только на **последнем этапе всей задачи** (у одноэтапной — на единственном) посмотри `npm run e2e -- stats`:
   полного прогона не было больше 7 дней — спроси человека, делать ли его перед финальной
   сдачей (навык `device`, «Журнал прогонов»). На предыдущих этапах этот вопрос не задавай.
5. Прочитай файлы из «Что прочитать». Сверь, что «Сейчас» в пунктах ещё правда.
6. Если в промпте есть «Вопросы, оставленные исполнителю» — задай те, что уже можно, одним
   инструмент вопросов Codex (см. `AGENTS.md`) (варианты, рекомендуемый первым), и работай над тем, что от них не
   зависит. Новые продуктовые развилки по ходу — так же, по разделу 10 CLAUDE.md.
7. Если есть инструмент списка задач — заведи задачи по блокам из «Порядок работы».

## 2. Работа

- По блокам из промпта. Блок доводится до рабочего состояния на телефоне, потом следующий.
- **Любые прогоны Maestro — только в самом конце последнего этапа всей задачи.** Если этапов
  шесть, на этапах 1–5 не запускай ни набор (`changed`, `--tags`, `full`), ни отдельные YAML.
  На этапе 6 не запускай Maestro между блоками: сначала закончи реализацию, точечную проверку
  на устройстве, тесты и ревью; затем один итоговый набор. До него проверяй блоки через
  `device.mjs`, записи/кадры, Jest и ручные сценарии. YAML можно написать заранее, но не гонять.
  Это правило имеет приоритет над советом навыка `device` запускать YAML при написании.
- Коммиты мелкие, Conventional Commits по-русски, как в `git log`. Миграции — отдельными
  коммитами `feat(db): …`.
- Миграция: файл в `supabase/migrations/`, RLS и индексы в той же миграции, применить к облаку
  (память `db-push-pooler-timeout`), перегенерировать `src/api/types.gen.ts`.
- Проверки: `npm run check` — tsc, eslint и jest параллельно, ~30 с, печатает только упавшее.
  Гоняй его один раз перед коммитом блока, а не после каждой правки и не цепочкой
  `tsc && eslint && jest` (подряд — вдвое дольше). Между ними, если нужно, — один
  `npx tsc --noEmit` или один тестовый файл `npx jest <путь>`.
- Проверочные запросы к базе — пачкой: несколько SELECT одним файлом, один вызов
  `npx supabase db query --linked -f <файл>` (каждый вызов ~20 с; про одну транзакцию на
  файл — память `db-query-file-one-transaction`).
- Нативный пакет или правка `plugins`/прав в `app.json` → пересборка dev build своими силами
  (память `android-local-native-build`), в отчёте сказать.
- За рамки задачи не выходи. Плохой код рядом — в отчёт, не в рефакторинг.

## 3. Самопроверка на телефоне

Человек промежуточные этапы не проверяет (память `agent-self-verifies-on-device`). Каждый
критерий приёмки ты проверяешь сам, на устройстве. Инструменты и приёмы — навык `device`;
загрузи его перед первой проверкой и держись его правила скорости: никаких `sleep`, ожидание
экрана — `wait`, цепочка действий — одной командой.

- разведка — `node scripts/device.mjs ui / tap / wait / shot`, жесты и анимации — `record`
  + `frames`;
- роли: посетитель-посторонний и участник, где это касается доступа; второе устройство и
  аккаунты — `test-devices-and-accounts`; Supabase с телефона — `supabase-blocked-without-vpn`;
- светлая и тёмная тема, если менялся вид;
- критерий с понятным путём «открыть → сделать → увидеть» в зоне, которую легко сломать
  (жесты, шиты, меню, отправка), — оформи сценарием Maestro в `.maestro/` и закоммить с
  фичей;
- сценарий проверь ручными действиями на устройстве; сам YAML запусти только в финальном
  Maestro-прогоне последнего этапа. «Нестабильно» — в отчёт, «упал» — чинить;
- окружение повело себя странно (белый экран, висит загрузка, ANR, пачка упавших сценариев,
  что-то повторилось второй раз) — сразу `node scripts/device.mjs reset`, без диагностики.
  Разбираться — только если после `reset` то же самое.
  Упавший старый сценарий — регресс, чинить его, а не сценарий (если поведение изменилось
  намеренно — поправь сценарий и скажи в отчёте).

Не вышло проверить критерий сам (нужен вход под живым аккаунтом, разрешение на устройстве,
второй человек) — помечай его «проверить человеку», не выдавай за проверенный.

## 4. Перед сдачей

1. `npm run check` — зелёный (tsc, eslint, jest). Падение не из-за твоих
   изменений — скажи явно, не чини молча.
2. Тесты на новое: поведение глазами пользователя, границы доступа обязательно (раздел 8
   CLAUDE.md).
3. Независимая проверка: запусти помощника Codex только для чтения по
   [инструкции проверяющего](references/acceptance-verifier.md). Передай ему диапазон
   изменений и полный список критериев дословно, с номерами, без своих выводов.
   Затем отдельным помощником проведи code review того же диффа: ошибки, регрессии,
   границы доступа и пробелы тестов, с местами в коде. Помощники не правят файлы.
   Если помощники недоступны, выполни обе проверки сам и явно отметь отсутствие
   независимого ревью. Найденное исправь или обоснуй в отчёте; после правок — шаг 1.
4. **Только в конце последнего этапа всей задачи:** когда все этапы завершены и правки по
   ревью внесены, один раз запусти `npm run e2e -- changed` (если охватывает все этапы),
   `--tags` с областями всех этапов или `full`, если человек выбрал его в шаге «Старт».
   На промежуточном этапе этот шаг пропусти.
   Упавшее исправь и перегоняй только упавшие сценарии по файлам, не весь набор заново.
5. Все свои изменения закоммичены. Заранее существовавшие посторонние правки перечисли в отчёте; не удаляй их ради чистого `git status`.

## 5. Отчёт человеку

Коротко, по разделу 2 CLAUDE.md, в таком порядке:

1. **Что сделано** — по пунктам промпта, по одной-две строки.
   Плюс строка про e2e: какой набор, где (телефон или эмулятор), итог; нестабильные
   сценарии — поимённо. На промежуточном этапе напиши «Maestro отложен до последнего этапа».
2. **Чек-лист для телефона** — только то, что человеку стоит потрогать руками: критерии,
   помеченные «проверить человеку», и самые важные по ощущению (жесты, анимации). Формат:
   экран → действие → ожидаемый результат, с номером критерия. Остальные критерии — одной
   строкой «проверены агентом на <устройство>: К1.1, К1.2, …».
3. **Ключевые скриншоты** — пути к файлам; если смотреть надо анимацию — к записи.
4. **Решения, которые стоит перепроверить** — из промпта («Что ещё отметить в отчёте») и твои.
5. **Что за доступом человека** — дашборд, секреты, сборка под iOS.
6. **Замечено за рамками задачи.**

Затем жди. Правки по замечаниям — в той же ветке, снова шаги 3–5. Мердж — только после
«мерджи»: `git merge --no-ff` в `master`, удалить ветку.
