# Проверка на устройстве

Используй актуальный `AGENTS.md` и общий
[протокол ожидания процессов](../../../docs/development.md#ожидание-процессов).
Подключай устройство к конкретной проверке, не автоматически в начале любой задачи.

- `node scripts/device.mjs <команда>` — окружение и ручная разведка. `help` — все команды.
  Зови через `node`, не через `npm run device --`: npm добавляет ~0,7 с к каждому вызову.
- `npm run e2e -- <набор>` (`scripts/maestro.mjs`) — сценарии из `.maestro/` с проверкой
  предпосылок, уборкой, ограниченным повтором и журналом `.maestro/stats.json`.
  Подробности запуска/совместимости APK — [окружение и сборки](../../../docs/development.md#окружение-и-сборки).

## Где проверять: телефон по умолчанию

Человек подключает свой realme (`df79e451`) и хочет, чтобы проверяли на нём: это в разы
быстрее эмулятора и честнее для видео и жестов.

1. `node scripts/device.mjs up --phone` к первой проверке берёт только подключённый телефон.
   Без флага режим тот же, даже если уже работает эмулятор или задан `ANDROID_SERIAL`.
2. Вышел с кодом 4 «Телефон не подключён» — **спроси человека** через инструмент вопросов текущего агента (см. `AGENTS.md`):
   «Подключил телефон» (рекомендуется) / «Не могу подключить — используй эмулятор». Подключил
   — снова `up`. Не может — `up --emulator`.
3. Если человек уже выбрал устройство в этой сессии, используй его ответ без повторного вопроса.
   Эмулятор — по разрешению человека. Сценарии с видео (метка `video`) на эмуляторе обёртка
   сама пропускает: там видео ненадёжно и на `master`.

Для проверки двух аккаунтов — `up --both`: телефон + один `OPEN_AVD` (по умолчанию `open_test`).
Выбирай этот режим, только когда задача требует двух устройств. `--second` больше не используется.
`reset --phone|--emulator|--both` перезапускает Open только на выбранных уже доступных устройствах;
выключенный эмулятор reset не запускает. `-s SERIAL` выбирает ровно одно устройство и не совмещается
с режимами. Для `ui`/жестов/`doctor` указывай `-s`, если подключены оба устройства.

На телефоне учитывай: жесты только когда Open наверху (скрипт проверяет сам), аккаунт —
память `test-devices-and-accounts`. Open использует self-hosted бэкенд; старое требование VPN
для Supabase Cloud не применяй автоматически. Сетевую ошибку проверяй по текущей конфигурации.

## Если проверка застряла

Сначала один короткий диагностический проход: `doctor`, затем `ui` или `shot` по симптому.
Установи, что мешает: Open не наверху, не та сборка, Metro/adb, сеть или тестовые данные.
Для видео недоступность дерева сама по себе не ошибка — смотри скриншот. Пустой список чатов
и экран входа также не доказывают зависание. Человек использует другое приложение — не сбрасывай
окружение; вернись в Open, когда это не мешает его действию.

Если подтверждён сбой, выбери компонент: `reset` — только Open на телефоне; `reset --component driver|metro|adb`
— явно выбранный компонент. `doctor --fix` восстанавливает reverse/часы и открывает Open.
`reset --component all -s <serial>` — последняя ступень после локальной меры; чужие процессы
и эмуляторы не завершаются. `up` и Maestro больше не выполняют автоматический полный reset.
Metro/adb — общие службы, их явный перезапуск затрагивает все соединения независимо от режима.
Повтор той же ошибки требует диагностики, а не нового reset. Логи — `.expo/agent-runtime/`.
`native: unknown` — неизвестно происхождение APK, не повод сразу пересобирать; `changed` —
проверить нативные входы. Release не подтверждает локальные JS-правки.

## Скорость

- **Ожидание экрана:** `tap` и `swipe` сами ждут цель до 10 с, результат — `wait <цель>` или
  `wait <цель> --gone`: возвращаются, как только экран готов. Не заменяй их `sleep` или
  собственным циклом снимков. Ожидание фоновой команды — по общему протоколу.
- **Цепочка — одним shell-вызовом**, с остановкой при ошибке каждого шага.
  В PowerShell после каждого `node scripts/device.mjs …` проверяй
  `if ($LASTEXITCODE -ne 0) { exit $LASTEXITCODE }`.
- **Рабочее окружение переиспользуй.** Metro и эмулятор не перезапускай перед каждым проходом.
- **`ui` — когда не знаешь, что на экране.** Знаешь цель — сразу `tap`/`wait`.

## Экран

- `ui` — компактное дерево: `#testID`, "текст", [подпись], `tap`, `focus`, центр `@x,y`.
- `tap <цель>`: `id:<testID>`, `text:<точный текст>`, `desc:<подпись>`, подстрока, `x,y`.
  Несколько совпадений — скрипт выведет их и попросит `--n`. `--long` — долгое нажатие.
  `text:` ищет по всему экрану: имя чата в шапке открытого чата — тоже совпадение.
- `wait <цель> [--gone] [--timeout сек]`, `swipe <цель> left 300 250`, `text <ascii>` (только
  латиница), `key back|enter|del`.
- `shot [имя]` — скриншот, путь к PNG: открой инструментом просмотра изображений текущего
  агента (см. `AGENTS.md`). При живом видео дерево экрана не отдаётся — смотри скриншотами.
- Анимации/рывки — [выбор измерения](../../../docs/development.md#выбор-визуального-измерения),
  затем [визуальные проверки](../../../docs/development.md#визуальные-проверки): `visual.mjs`
  записывает один маршрут Maestro или ручной проход, возвращает краткий отчёт и артефакты.
  `record <сек> [имя]` остаётся простым scrcpy-захватом; `frames` без fps выгружает все кадры —
  для первичного просмотра используй ограниченный лист `visual.mjs frames`.
- К списку чатов из любого места без перезапуска:
  `adb -s <serial> shell am start -a android.intent.action.VIEW -d openger://chats`.

Нужного `testID` нет — добавь его в компонент: это дешевле координат и пригодится Maestro.

## Сценарии Maestro

У каждого сценария в шапке `tags:` — области (`chats`, `comments`, `channels`, `pops`,
`media`, `subscriptions`, `search`), `smoke` у дыма, `video` у тех, где открывается видео.

| Набор                              | Что идёт                                                            | Когда                                                                 |
| ---------------------------------- | ------------------------------------------------------------------- | --------------------------------------------------------------------- |
| `npm run e2e -- <файл.yaml>`       | конкретные сценарии                                                 | пишешь или чинишь сценарий                                            |
| `npm run e2e -- changed`           | дым + области, которые трогает ветка, + изменённые в ветке сценарии | перед сдачей, если риски требуют набора; не после каждого блока       |
| `npm run e2e -- --tags chats,pops` | дым + названные области                                             | ветка трогает общее, а `changed` промахивается                        |
| `npm run e2e -- full`              | все                                                                 | по просьбе человека или при обоснованном риске для приложения целиком |

Небольшой задаче достаточно целевого прохода/сценария, подтверждающего её критерии.
Перед выбранным прогоном посмотри `npm run e2e -- stats` и проверь необходимые аккаунт,
чаты/каналы и данные выбранных сценариев. Набор не запускают только ради давности журнала.
В многоэтапной задаче общий набор планируй на финал; промежуточный этап проверяй адресно,
если человек не задал иной объём. При общей отсутствующей предпосылке действуй по протоколу
ожидания: не продолжай одинаковые таймауты и автоматические повторы.

`--plan` показывает выбор без устройства/установки CLI. `--preflight` проверяет окружение и
объявленные в выбранных сценариях CHAT/CHANNEL/ID/ссылки, без уборки и исполнения тестов.
Эта проверка наличия не подтверждает права аккаунта или весь контент сценария.
Обёртка использует текущее приложение, снимает драйвер Maestro и атомарно убирает тестовый мусор
(`scripts/e2e-reset.sql`). Повтор отдельного падения — максимум один, с перезапуском только Open.
Общая/повторная одинаковая ошибка останавливает очередь и повторы, сохраняя диагностику.
Итог: **ок**, **нестабильно** (прошёл со второго раза), **упал**; невыполненное не засчитывается.
Два падения сами по себе не доказывают регресс; отличай ошибку кода, сценария, данных и среды.
Нестабильность и непроверенные критерии укажи в отчёте, критичный результат подтверди отдельно.
Не подгоняй ожидания теста под баг. `--no-reset` пропускает только уборку, `--no-retry` — повтор.
SQL идёт через `TARGET_SSH_HOST` или `TARGET_DB_URL` текущего self-hosted сервера. Ошибка подготовки
завершает запуск до сценариев; не обходи её через `--no-reset`. Полный вывод — в `maestro.log`
рядом с JUnit; в чат передавай конкретный сбой и путь к логу.

### Журнал прогонов и полный прогон

`.maestro/stats.json` (не в git, живёт на машине между ветками) пишет сама обёртка: по каждому
сценарию — прогоны, ок / нестабильно / упало, последние 10 итогов, последняя проблема и её
текст, среднее время; и `lastFullRun` — когда был полный прогон и чем кончился.
`npm run e2e -- stats` — сводка, сверху самые проблемные.

- Возраст последнего полного прогона — информация, не требование нового прогона.
  Выбирай набор по риску текущей задачи.
- Сценарий упал — сравни с журналом и установи причину. Повторяй отдельно после изменения
  условия или исправления; уже выполненный автоматический повтор тоже учитывается.

### Как писать сценарий

- Цели — по `id:` (testID) и точному тексту; координаты не используй.
- Вход — `runFlow: subflows/open-app.yaml` (ссылкой к списку чатов, перезапуск только если
  Open не загружен). Не забудь `tags:` в шапке.
- Чат по умолчанию — `env: CHAT` в шапке («Plany»); на другом аккаунте — `-e CHAT=<имя>`.
- Сценарий убирает за собой в том же прогоне; тестовые тексты — латиницей с префиксом
  `maestro-` и меткой времени (`evalScript: ${output.msg = 'maestro-' + Date.now()}`): по
  префиксу их находит уборка. Новый вид мусора (подписка, закреп, реакция в другом месте) —
  допиши его уборку в `scripts/e2e-reset.sql`.
- Сценарий проверяет поведение (появилось, исчезло, в фокусе), а не вид. Плавность и вид —
  запись и скриншоты.
- Писать его стоит для фичи с понятным путём «открыть → сделать → увидеть», который легко
  сломать соседними правками (жесты, шиты, меню, отправка), — вместе с фичей, в том же коммите.

## Чего не делать

- Не менять настройки защиты устройства (Play Protect и т. п.) — только просить человека.
- Не трогать старые сообщения тестовых аккаунтов и личные фото в галерее
  (`test-devices-and-accounts`).
