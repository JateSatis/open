# $optimize — от замера до приёмки

Задача — промпт в переписке. Прочитай `AGENTS.md`, `CLAUDE.md` и память по их указанию.
Загрузи `.agents/skills/implement/SKILL.md` и **выполни весь его цикл**: ветка и сохранение
посторонних правок, окружение, реализация блоками, `device`, `npm run check`, тесты,
независимые проверки, один итоговый набор Maestro, коммиты, отчёт человеку, ожидание
проверки и мердж только после явного согласия. При оптимизации добавь следующие шаги.

## До первой правки поведения

1. Назови критический путь глазами пользователя: от тапа до первого видимого отклика,
   первого кадра с **правильной конечной точкой**, завершения перехода, загрузки окружения
   и тяжёлого медиа. Скелетон и спиннер не считай готовым содержимым. Внутри чата и между
   экранами измеряй отдельно.
2. Зафиксируй baseline на том же устройстве и том же наборе данных, на котором сравнишь
   результат. Раздели тёплый кеш, холодный кеш и медленную сеть. Проводя серию повторов,
   записывай хотя бы медиану, p95, худший случай и число неверных первых кадров. Если
   сценарий нельзя воспроизвести автоматически, запиши конкретный ручной маршрут и видео.
3. Инструментируй этапы, чтобы видеть причину, а не угадывать: время JS (`performance.now`),
   сетевые запросы и их зависимости, React Profiler/число рендеров, JS и UI кадры, Android
   `SurfaceFlinger`/Perfetto. Проверяй на release или сборке без dev overhead для итоговых
   цифр; debug используй для поиска причины. Метки разных потоков сопоставляй через
   согласованные часы или видео; не смешивай их абсолютные времена без калибровки.
4. Нарисуй короткий граф зависимостей загрузки. Выдели то, что требуется для первого
   правильного кадра, что можно взять из кеша/ссылки, начать на касании, загрузить параллельно
   либо отложить после анимации. При неясном узком месте сделай один проверочный эксперимент.

## Цикл ускорения

- Меняй один узкий участок за раз; после него повтори тот же сценарий и сравни цифры.
  Не оставляй оптимизацию с нулевым или отрицательным эффектом лишь потому, что она выглядит
  элегантно. Сохраняй пользовательское поведение и права доступа.
- Переноси тяжёлую работу за первый правильный кадр, если это не оставляет неверную цель
  на экране. Кешируй и прогревай только там, где замер показывает выигрыш без торможения
  критической анимации; ограничивай срок жизни, объём и отменяй устаревшие запросы.
- Готовый кадр важнее полной загрузки. Позиция цели должна быть известна к первому
  видимому кадру содержимого, без скрытой цепочки `scrollToIndex`, повторных таймеров
  и прыжка после появления. Короткая иллюзия прокрутки допустима, если её кадры ровные.
- Для сложных списков измеряй стоимость создания и обновления ячеек, работу на JS и UI
  потоках, скачки от изображений и изменение позиции при догрузке. Запросов меньше —
  не всегда быстрее: проверяй время первого содержательного ответа и общий критический путь.
- Используй возможности проекта прежде новых зависимостей. Устаревшие трюки из прошлых
  задач не копируй автоматически: изучи текущий код и проверь гипотезу замером.

## Инструменты и эталон

- `.agents/skills/device/SKILL.md`: `device.mjs record`, `frames`, скриншоты и точечные
  сценарии; на realme запись через scrcpy. Видео помогает доказать последовательность
  видимых кадров, но сама запись может замедлять Modal — контрольный прогон без неё обязателен.
- `src/features/media/perf.ts`: временные метки, счётчики рендеров/монтирований и зонд
  JS-кадров за флагом. Адаптируй приёмы для конкретного сценария; в обычной сборке
  инструментация выключена или удалена. React Native DevTools Profiler — для JS,
  Perfetto/FrameTimeline или `dumpsys SurfaceFlinger --latency` — для нативных кадров,
  логи клиента/API и Postgres `EXPLAIN (ANALYZE, BUFFERS)` — для сети и SQL по необходимости.
- [Кейс media-шита](references/media-sheet-case.md) — прочитай, когда выбираешь способ
  измерения или планируешь перенос тяжёлого содержимого за анимацию. Это результаты
  конкретных устройств и сборок, а не норматив для всех экранов.
- Версии Expo и React Native сверяй с `AGENTS.md` и точной документацией установленного SDK
  перед правкой кода. Android: ориентир 16,7 мс на кадр при 60 Гц, отсутствие кадров
  дольше 700 мс; эти числа не являются обещанием сетевого ответа.

## Перед сдачей

В дополнение к отчёту `$implement` дай таблицу «сценарий / до / после» для каждого
критического перехода: первый отклик, первый правильный кадр, p50/p95, худший кадр,
состояние кеша, устройство и тип сборки. Приложи запись или кадры, показывающие первый
видимый экран и анимацию, и граф оставшихся сетевых зависимостей. Отдельно назови
неподтверждённые гипотезы и случаи, где целевой порог не достигнут. Не выдавай
субъективное ощущение, Jest или Maestro за измерение скорости.
