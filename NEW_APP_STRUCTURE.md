# Open — структура новой версии приложения

Этот документ фиксирует целевую архитектуру Open и порядок постепенного переноса. Его можно передать агенту вместе с задачей на один шаг. Текущее дерево отражает ход разработки, а примеры путей ниже показывают, куда должен прийти код. Общие правила работы в репозитории описаны в [AGENTS.md](AGENTS.md).

## Два дерева на время перехода

Перенос начинаем от `master` после слияния завершённой работы над запуском. Старое приложение целиком сохраняется в `src/` как образец поведения. Новую версию пишем в `src/new_app/` и запускаем её с первого шага.

```text
src/
├── index.tsx           прежняя точка входа
├── api/, features/, …  прежняя реализация
└── new_app/
    ├── index.tsx       самостоятельная точка входа
    ├── ui/
    ├── controllers/
    └── services/
```

На первом шаге создаём новый `index.tsx` с нуля и меняем поле `main` в [package.json](package.json) на `./src/new_app/index.tsx`. Новый вход сам регистрирует приложение в Expo. Старый `src/index.tsx` сохраняет свой путь и содержимое. Критерий первого шага — при холодном запуске заставка уходит и появляется узнаваемый первый экран новой оболочки.

У нового клиентского кода одна граница: зависимости внутри `src/` ведут только в `src/new_app/`. Это касается и косвенных импортов. Старый код читаем, сверяем и переносим по частям. Импорт старого корня, компонента или стора через обёртку нарушил бы эту границу. Пакеты, ресурсы из `assets/` и нативные модули из `modules/` можно использовать из обеих версий. Для внутренних импортов подходят относительные пути либо отдельный алиас с корнем в `new_app/`.

## Три слоя

За основу взята аналогия с MVC. Для выбора папки используем обязанности из таблицы. До финального переноса все пути слоёв отсчитываются от `src/new_app/`, после него — от `src/`.

| Слой | Что ему принадлежит | Как организованы папки |
| --- | --- | --- |
| **`ui/`** | Экраны, компоненты, отображение, обработка действий пользователя, правила и состояние конкретного интерфейса. UI вызывает операции контроллера и показывает их результат. | По разделам приложения, экранам и компонентам. |
| **`controllers/`** | Операции на языке Open, продуктовые правила, данные и состояние, необходимые для выполнения операции. Контроллер выбирает данные и определяет последовательность действий. | По предметным областям, например `messages/`, `channels/`, `accounts/`, `calls/`. Внутри — связанные операции. |
| **`services/`** | Технические возможности: выполнить запрос, провести транзакцию SQLite, прочитать файл, поддерживать подписку, отследить соединение. Сервис получает параметры и отвечает за механизм выполнения. | По виду работы, например `backend/`, `database/`, `files/`, `realtime/`, `connection/`. |

Основное направление зависимостей — **`ui → controllers → services`**. Контроллеры могут пользоваться другими контроллерами, сервисы — другими сервисами. Сервис может возвращать результат или публиковать событие через подписку. Смысл события для Open определяет контроллер. Корень приложения связывает слои, подключает провайдеры и задаёт время жизни общих подписок. Локальное действие интерфейса, например раскрытие меню, целиком выполняется в UI.

### Как выбрать владельца

- **UI.** Начальные ориентиры — `ui/auth/`, `ui/feed/`, `ui/chats/`, `ui/profile/` и `ui/shared/`. У экрана один адрес по смыслу, даже если в него ведут несколько вкладок. Для самостоятельного интерфейса поверх вкладок допустима своя область, например `ui/calls/`. В `shared/` подходят общие элементы вроде кнопки, диалога или панели с жестами. Компонент переписки может обслуживать и чат, и канал, оставаясь в `ui/chats/`.
- **Состояние.** «Локальное» означает «принадлежит странице или компоненту». Список выделенных сообщений принадлежит UI переписки. Очередь отправки продолжает работу после закрытия экрана и принадлежит `controllers/messages/`. Выбор между Zustand, React state и хранением на диске сам по себе не определяет слой.
- **Контроллер.** Путь к операции читается как `controllers/<область>/<операция>`, например `controllers/messages/sendMessage.ts`. Здесь решается, когда поставить сообщение в очередь, загрузить вложения и принять подтверждение сервера. Простая операция вроде получения канала может состоять из одного запроса. Родственные небольшие функции можно держать в одном файле.
- **Сервис.** Для выполнения запроса сервис вправе получить имя RPC и значения полей. За выбор RPC, трактовку ответа и правила канала отвечает `controllers/channels/`. Аналогично, `services/database/` знает, как провести транзакцию, а контроллер сообщений знает, когда сохранить историю. Общий механизм может обслуживать всё приложение, при этом запрос, кеш и подписка сохраняют своего владельца при переключении аккаунтов.

### Как читать старую папку api

Общего аналога `src/api/` в целевой схеме нет. Разбираем файл в рамках переносимого сценария. Ниже примеры границ, которые уже видны в старой реализации.

| Сейчас | Целевое место |
| --- | --- |
| Создание клиента Supabase, таймауты и схема сервера | `services/backend/`. При переносе генерируемой схемы обновляем и команду генерации. Общая настройка кеша TanStack Query относится к отдельному виду работы — `services/query/`. |
| Получение канала в `src/api/channels.ts` | `controllers/channels/`. Контроллер выбирает сведения о канале и преобразует ответ, пользуясь клиентом из `services/backend/`. |
| Серверная отправка в `src/api/chats.ts` и доставка в `src/features/chats/messages/delivery.ts` | Один вход для экрана в `controllers/messages/`. При переносе учитываем очередь, отправку и подтверждение, даже если старый код разнесён по папкам. |
| `signedUrls.ts`, `avatars.ts`, `chatMedia.ts` в `src/api/` | Общий механизм подписания ссылок — `services/backend/storage/`. Выбор бакета и срока ссылки для аватаров и вложений — `controllers/media/`. |
| Подписки на события чатов, комментариев и попов | Соединение и совместная подписка на топик — `services/realtime/`. Выбор топика, аудитории и реакция на событие — у контроллера соответствующей области. |

## Тесты

**Jest.** Каждый тест новой версии лежит в подпапке `test/` ближайшего владельца поведения. Примеры — `ui/shared/Button/test/Button.test.tsx` и `controllers/messages/delivery/test/retrySend.test.ts`. Тестовые помощники конкретного модуля лежат там же. Сохраняем суффиксы `.test.ts` и `.test.tsx`.

Корневой `new_app/test/` появляется по конкретной необходимости: тест сборки приложения целиком или общая тестовая поддержка для нескольких областей. При первом тесте новой версии проверяем настройку Jest в [package.json](package.json): сейчас там явно подключаются setup и мок стилей из старого `src/test/`. Оригинальные тесты остаются со старой реализацией до завершения переноса.

**Maestro.** Пользовательские сценарии на устройстве живут в корневой `.maestro/`. На переходный период сценарии, доступные в новой оболочке, собираем в `.maestro/new_app/`. С первым таким сценарием добавляем явный выбор нового набора: текущий [скрипт запуска](scripts/maestro.mjs) ищет YAML только непосредственно в `.maestro/`. Первый сценарий — холодный запуск нового приложения. После перехода временное деление по версиям можно убрать.

## Как выполнять один шаг

1. Выбрать один проверяемый результат в новой версии. Например, пользователь вводит занятое имя и видит соответствующее сообщение. Зафиксировать, как этот сценарий ведёт себя в старой реализации.
2. Найти старые точки входа и зависимости именно этого сценария. Разнести обязанности по новым слоям. Папки и абстракции добавлять по мере появления кода.
3. Подключить результат через новую точку входа. Старую реализацию и её тесты сохранить, включая файлы, у которых в новой версии уже есть полноценная замена. Если старое поведение изменилось параллельно, сверить это изменение с новой версией.
4. Проверить перенесённое поведение подходящими тестами. В отчёте указать, что теперь работает в новой версии, куда попал код, как проверить результат на телефоне и какие отличия от старого поведения согласованы.

Перенос завершается отдельной задачей после приёмки новой версии целиком. В ней удаляем старый клиентский код из `src/`, поднимаем содержимое `src/new_app/` в `src/`, возвращаем `main` на `./src/index.tsx` и обновляем пути в импортах, настройках, тестах, скриптах, генераторах и карте проекта. Завершающая проверка включает холодный запуск и пользовательские сценарии из окончательного расположения.
