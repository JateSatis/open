# Разработка: команды, структура, код, тесты

Справочник рабочего процесса. Читай выбранный раздел по [карте](map.md#нужны-правила).
Оглавление: `node .agents/scripts/read-doc.mjs docs/development.md`.

## Команды и сборка

Перед сдачей изменений приложения — `npm run check`: TypeScript, ESLint и Jest параллельно,
с выводом упавшего. Длительность зависит от окружения; отсутствие вывода не означает зависание.
Не запускай те же проверки отдельно следом за успешным `check`, если код не менялся и новых
рисков нет. Внутри итерации достаточно целевого теста/проверки; после исправлений повторяй
затронутое, перед сдачей — итоговый `check`. Падение не из-за изменений явно укажи,
не чини молча и не подавляй; свою падающую проверку исправь до сдачи.
Для изменений только инструкций/навыков — `node .agents/scripts/check-instructions.mjs`,
формат и дифф; приложение собирать и тестировать не нужно.
Если меняешь механизм чтения/проверки документации — дополнительно
`node --test .agents/scripts/doc-navigation.test.mjs` (без Jest, устройства и сети).

```bash
node scripts/device.mjs up --phone # запуск на телефоне (также режим по умолчанию)
node scripts/device.mjs up --emulator # один эмулятор OPEN_AVD, по умолчанию open_test
node scripts/device.mjs up --both # телефон и этот эмулятор
npm start               # Metro без USB
npm run build:android   # пересобрать dev build в облаке EAS
npm run build:ios       # то же для iPhone
npm run device -- up    # агенту: телефон (нет — спросить), Metro, Open открыт (навык device)
npm run device -- reset # перезапуск только Open; другие компоненты — явно, см. ниже
npm run e2e -- changed  # Maestro: дым + затронутое; full — все; stats — журнал
```

JS прилетает с Metro мгновенно; нативная часть вшита в APK. Пересборка — только при изменении
нативного (пакет, `plugins`, `scheme`, id/права в `app.json`, обновление SDK); TS-фичи — без
пересборки. Готовая сборка — `adb install`; `eas-cli` — глобально (не в зависимостях — иначе `npm ci`
на билдере ломается). Id: `com.openger.app` обе платформы, схема `openger`; менять только вместе и до
публикации.

Android EAS-профили `preview` (APK) и `production` (AAB) сохраняют Gradle/CMake cache между
сборками. Ключ `open-android-sdk57-native-v1` менять при обновлении Expo SDK, нативных зависимостей,
плагинов или конфигурации Android; одинаковый ключ переиспользует результаты компиляции нативной
части. URL и anon key для обоих профилей хранятся в EAS environments `preview` и `production`.

## Окружение и сборки

`node scripts/device.mjs up` — единый запуск для человека и агента: выбранные устройства,
проверка установленной сборки, Metro своего проекта (только для dev build), reverse и открытие Open.
Команда завершается после проверки; Metro остаётся скрытым процессом с логом в
`.expo/agent-runtime/`. `npm start` по-прежнему оставляет Metro в текущем терминале.
Режимы `up` и `reset`: `--phone` (по умолчанию), `--emulator` (один `OPEN_AVD`, обычно `open_test`),
`--both` (телефон + этот эмулятор). Флаги без команды означают `up`, например
`node scripts/device.mjs --phone`. Для точного устройства — `-s SERIAL`, без сочетания с режимами.
`ANDROID_SERIAL` не меняет выбор у `up`/`reset`; у остальных команд он сохраняется.
`--second` удалён. Только `up --emulator`/`up --both` запускает недостающий эмулятор;
`reset` работает с уже доступными выбранными устройствами и не запускает выключенные.

Пустой список чатов и экран входа — допустимые состояния приложения. Для Maestro нужен
авторизованный тестовый аккаунт; наличие заданных в сценарии чатов/каналов проверяется отдельно.
`doctor` показывает устройство, версию и тип APK, Metro, reverse, часы, доступность Auth/REST
с компьютера и путь к диагностике. Это не проверка сети телефона или прав его аккаунта.

Восстановление — один раз для установленной причины:

- `doctor --fix` — reverse/часы и открыть Open;
- `reset --phone` (или просто `reset`) — только Open на телефоне;
- `reset --emulator` / `reset --both` — Open на выбранном эмуляторе / обоих устройствах;
- `reset --component driver` — только драйвер Maestro;
- `reset --component metro` — только Metro, созданный этим инструментом (PID и команда проверяются);
- `reset --component adb` — сервер adb; `reset --component all -s SERIAL` — явное восстановление
  Open/драйвера/управляемого Metro/adb. Чужие процессы и эмуляторы не завершаются.
  Metro и adb — общие службы; их явно запрошенный перезапуск влияет на все подключения,
  даже с `--phone`. Обычный `reset` их не перезапускает.

Совместимость APK: `node scripts/dev-build.mjs status -s SERIAL`. Используется Expo Fingerprint,
а не дата APK или версия JS. Состояния: `compatible`, `changed`, `unknown`.
`unknown` означает отсутствие проверенной записи этой установки, не требование новой сборки.
При `changed` сравни нативные входы и подбери совместимую сборку; новую запускай только если нужна.
Release не загружает локальные JS-правки через Metro.

Установка известного артефакта: `node scripts/dev-build.mjs install -s SERIAL --build EAS_BUILD_ID`.
Команда проверяет проект/приложение/завершение EAS-сборки, скачивает APK, устанавливает его и
сверяет SHA-256 установленного файла. Локально сохраняются build ID, fingerprint и сведения
об установке; переустановка другим способом делает такую запись неактуальной.
Новая сборка автоматически не заказывается. Актуальный fingerprint вычисляет Expo по нативным
входам проекта; отдельный вручную составленный кеш зависимостей не используется.

Maestro: `node scripts/maestro.mjs --plan <набор>` — только выбор сценариев, без устройства/установки.
`--preflight` — окружение и наличие объявленных CHAT/CHANNEL/ID/ссылок, без уборки и тестов.
SQL использует явно заданный `TARGET_SSH_HOST` или `TARGET_DB_URL` по
[правилам self-hosted](backend.md#миграции-типы-переменные-окружения). Ошибка предпосылки/уборки
останавливает запуск. Уборка транзакционная; `--no-reset` пропускает только её, не диагностику.
Повторная общая ошибка останавливает оставшиеся сценарии и повторы; они не считаются прошедшими.
Полный вывод Maestro — в `maestro.log` рядом с JUnit, краткий итог — в терминале.
Проверка обёрток: `node --test scripts/dev-runtime.test.mjs scripts/device-selection.test.mjs`
(без Jest, устройства и сети).

## Ожидание процессов

Общий протокол для Codex, Claude и Kimi: один запуск → идентификатор → ожидание → итог.
Он относится к сборкам, установке и тестам; ожидание элемента экрана — в навыке `device`.

- Перед запуском выбери признак завершения и разумный таймаут операции. Сохрани session/task/build
  ID и путь к логу, если он есть. Повторная команда запуска создаёт новую работу, а не проверяет старую.
- Пока процесс идёт, делай независимую работу. Затем используй уведомление о завершении или
  блокирующее ожидание результата с возвратом при новых данных. Если известна длительная операция,
  выбирай окно ожидания 30–60 с в пределах возможностей инструмента; отдельный вызов не дольше 60 с.
  Не делай коротких опросов каждые 1–5 с и не перечитывай полный лог на каждом шаге.
- Codex: после `exec_command`, вернувшего `session_id`, — `write_stdin` с пустым вводом и
  `yield_time_ms: 30000` или `60000`. `functions.wait` нужен только после `functions.exec`,
  вернувшего `Script running with cell ID`; это другой идентификатор, не shell session ID.
- Claude/Kimi: фоновый `Bash` (`run_in_background=true`, когда поддерживается), затем штатное
  уведомление/ожидание результата того же task ID. Не заменяй ожидание серией `sleep` + чтение лога.
- Для удалённой сборки используй CLI, умеющий ждать её завершения. Если доступен только status API,
  ограниченный по времени опрос одного build ID можно выполнять внутри одного фонового процесса
  с паузами 30–60 с и выводом только смены состояния. Продолжай по этому ID, не запускай сборку заново.
- Пустой вывод или истечение окна ожидания означает «ещё работает». Таймаут всей операции означает
  «результат неизвестен»: проверь её состояние и причину задержки. Не убивай здоровый процесс только
  ради экономии токенов. Новый запуск — после подтверждения, что прежний завершён/остановлен,
  и изменения условия, вызвавшего сбой; бесконечных повторов одного сбоя быть не должно.
- По завершении проверь код выхода/конечный статус и нужный артефакт или критерий. В отчёт — итог,
  длительность, конкретная ошибка и ссылка на лог; большие логи читай только вокруг ошибки.
  Успешный старт, появление файла или пустой лог не подтверждают успешное завершение.
- Если набор тестов упирается в доказанную общую причину (например, нет обязательного тестового
  чата), останови этот прогон и его автоматические повторы, сохрани результаты и исправь предпосылку
  либо отметь непроверенное. Не повторяй весь набор, пока условие не изменилось.
- Сообщай о результате, новой проблеме или требуемом действии; соблюдай правила обновлений текущего
  агента, не пересказывая неизменный статус. Нужен ответ человека — сохрани вопрос и ID процесса;
  молчание не означает согласие. При передаче работы укажи, что ещё запущено и как получить итог.

## Структура проекта

```text
src/app/              маршруты Expo Router: (auth)/, (tabs)/ чаты-лента-профиль
src/components/       переиспользуемый UI без домена
src/features/         фичи по сценариям; актуальные точки входа — в docs/map.md
src/api/              supabase.ts (клиент один раз), types.gen.ts (не редактировать),
                      <domain>.ts (запросы по доменам), signedUrls.ts
src/store/            общее состояние; доменные сторы также внутри features/
src/theme/            цвета, типографика, отступы, тени
src/lib/              общие утилиты
supabase/migrations/  SQL-миграции (единственный источник правды схемы)
supabase/functions/   Edge Functions
```

Код группируется по фичам, не по типам файлов (экран + хуки + типы рядом). Компонент — папка:
`index.tsx` + `styles.ts` + `*.test.tsx`.

Продуктовый запрос → код/API/проверки: [карта проекта](map.md). Открывай только нужную область.

## Код

- TS: `any` запрещён; серверные типы — из `src/api/types.gen.ts`, не переобъявлять; экспорт
  компонентов именованный (default — только файлы маршрутов Expo Router).
- Стили: без магических чисел; цвета/отступы/шрифты — из `src/theme/`, новый токен — в тему.
- Компоненты: функциональные; один экспортируемый на файл; >~150 строк — разбивай.
- Списки: сообщения и лента — виртуализированные с пагинацией; никаких `map` по сообщениям и
  `ScrollView` для переписки.
- Именование: компоненты/папки PascalCase, хуки useCamelCase, остальное camelCase.
- Комментарии — «почему», не «что».
- Платформы: безопасные зоны — `react-native-safe-area-context`; клавиатура+поле ввода — самое
  проблемное место, проверять отдельно; `Platform.select`; `.ios.tsx`/`.android.tsx` — только если
  различий много. Человек проверяет на Android (iPhone — когда будет Apple Developer): это не повод
  ломать iOS.

## Тесты

- Новый экран и компонент с логикой — с тестом; поведение глазами пользователя; тест рядом с файлом.
- Сеть/Supabase/LiveKit в тестах всегда замоканы.
- Границы доступа — обязательно (ядро продукта): участник пишет сообщение, посторонний нет;
  посторонний комментирует/реагирует везде; слушатель стрима не публикует поток.
- Тесты — страховка агента, не доказательство для человека; проверяет человек руками.

## Выбор объёма проверки

Внутри итерации: `npm test -- --findRelatedTests src/путь.ts --runInBand --silent` для логики
или `--runTestsByPath src/путь.test.tsx` для известного теста. Отсутствие найденных тестов —
пробел покрытия, не успех; не добавляй `--passWithNoTests`. Перед сдачей изменений приложения —
полный `npm run check` один раз по [командам и сборке](#команды-и-сборка).
Статические импорты не покрывают маршрутизацию, конфигурацию, нативные зависимости и динамические
связи: для них выбери явные тесты затронутых сценариев. Jest не измеряет задержки устройства.

Maestro: конкретный сценарий → область по риску → полный набор только при необходимости.
`node scripts/maestro.mjs smoke` включает несколько сценариев, в том числе комментарии с данными;
`node scripts/maestro.mjs .maestro/smoke.yaml` — только запуск и вкладки, без чатов-фикстур.
Сначала `--plan`/`--preflight`, если неизвестны выбор/данные. Отсутствующая фикстура — блокировка
проверки, не повод 30 раз ждать её в разных тестах. Журнал содержит старые падения среды и продукта;
не удаляй тесты по проценту падений. Исправляй один воспроизводимый сбой и подтверждай отдельно.
`--no-reset` сохраняет данные и требует сценария, который убирает собственные изменения.

Для host-скриптов: ESLint затронутых JS-файлов и соответствующие `node --test`, без сборки APK.
Для механизма визуальных проверок — `node --test scripts/visual.test.mjs` и короткий захват на телефоне.

## Визуальные проверки

`node scripts/visual.mjs help` — команды. Захват по умолчанию только на подключённом телефоне;
эмулятор не стартует. Требуются разблокированный экран, открытый Open нужной сборки и аккаунт.
Захват проверяет активное приложение и объявленные фикстуры, но не запускает окружение,
не проверяет совместимость локального кода с APK и не подтверждает сеть. Для запуска/совместимости —
`device.mjs up`/`doctor` по [окружению и сборкам](#окружение-и-сборки). Сценарий — существующий
`.maestro/<имя>.yaml`; `--flow smoke` здесь означает ровно файл `smoke.yaml`, не набор smoke.
Подготовка выполняется до записи, уборки данных и автоматических повторов нет. Сценарий должен
заканчиваться в пределах `--seconds` (3–120); иначе итог failed, даже если есть видео.

```bash
node scripts/visual.mjs capture --mode video --flow smoke --seconds 60 --label before --gestures --conditions "release; warm cache; same account/network"
node scripts/visual.mjs capture --mode trace --flow smoke --seconds 60 --label before --conditions "release; warm cache; same account/network"
node scripts/visual.mjs frames "путь/video.mp4"
node scripts/visual.mjs analyze "путь/trace.perfetto-trace"
```

Без `--flow` — ручной маршрут после сообщения READY, результат остаётся unverified.
Видео: касания показаны `show_touches`, с `--gestures` — ещё траектория `pointer_location`.
Это диагностические оверлеи, они меняют картинку: для сравнения геометрии делай чистый скриншот.
Клавиатура/Back и шаги Maestro — в его debug-артефактах; не каждое взаимодействие является касанием.
Настройки восстанавливаются при успехе/ошибке/Ctrl+C. При отключённом USB или жёстком убийстве
процесса подключи телефон и выполни `node scripts/visual.mjs restore "каталог результата"`.

Читай сначала `.expo/agent-runtime/visual/<запуск>/summary.json`: условия, сборка, статус,
метрика/ошибка. Логи, исходный сценарий, JUnit/debug, видео или трасса лежат рядом, в git не идут.
`actions.json` — короткая лента действий Maestro с началом/длительностью команд. Эти времена
включают поиск цели и ожидания, не являются моментом касания и не синхронизированы точно с PTS видео.
`frames` создаёт один лист из 8 кадров; он может пропустить короткую вспышку. При известном моменте
извлеки через ffmpeg только этот интервал, не тысячи кадров всей записи. Видео scrcpy имеет
переменную частоту: длительность/редкие обновления не равны фризу приложения.

Perfetto: Android 12+, локальный trace_processor скачивается один раз, проверяется SHA-256.
Отчёт относится ко всему окну захвата и кадрам процесса Open, объединённым по surface frame token;
там есть подготовительные действия Maestro/ожидания. Для одного перехода запиши отдельный короткий
маршрут или исследуй его интервал в Perfetto UI. Ноль кадров/потеря данных — no-frame-data/incomplete,
не «0% рывков». При малом числе кадров процент рывков не характеризует плавность сценария.
Видео/SurfaceView и скорость появления правильного контента проверяются отдельно.
Не собирай видео и трассу одновременно для сравнительного замера: запись создаёт нагрузку.

OpenCV нужен только для численного сравнения двух одинаково снятых областей. Установка один раз
в host-venv (PowerShell; после ошибки остановиться): `python -m venv "$env:LOCALAPPDATA/open-tools/visual-venv"`,
затем `& "$env:LOCALAPPDATA/open-tools/visual-venv/Scripts/python.exe" -m pip install --only-binary=:all: opencv-python-headless==4.13.0.92`.
Вызов тем же Python: `scripts/visual-compare.py before.png after.png --roi X Y W H`.
Результат — процент отличающихся пикселей и diff, без автоматического вердикта «правильно».
Не включай в ROI часы, видео, мигающий курсор и оверлеи касаний; не меняй размер изображений молча.
Проверка самого анализатора тем же Python: `scripts/visual-compare.test.py`.

Основания инструментов: [scrcpy recording](https://github.com/Genymobile/scrcpy/blob/v3.1/doc/recording.md),
[FrameTimeline](https://perfetto.dev/docs/data-sources/frametimeline),
[Jest findRelatedTests](https://jestjs.io/docs/29.7/cli#--findrelatedtests-spaceseparatedlistofsourcefiles).

## Чего не делать в коде

- Таблицу без RLS-политик в той же миграции.
- Секреты в клиенте (всё `EXPO_PUBLIC_` попадает в бандл).
- Смешивать комментарии посторонних с сообщениями (ни в базе, ни в UI).
- Ограничивать права только в интерфейсе: серверное ограничение первично, скрытая кнопка — дополнение.
- Обещать в интерфейсе приватности, которой нет.
- «Чинить» падающие тесты правкой ожиданий.
