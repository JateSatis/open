# Openger (Open)

Общие правила работы. Общайся по-русски.

## Как читать

1. Этот файл — всегда. Есть актуальные пути и ограничения в переданном контексте — начни с них.
   Иначе выбери сценарий в [карте проекта](docs/map.md) и открой одну нужную карточку/точку входа.
2. Карточка — навигатор по коду, не второй справочник правил. Подробные правила хранятся один раз
   в справочниках; карта направляет в конкретный раздел, когда он нужен для изменения.
   Не загружай все карточки, все справочники или все документы с упоминанием темы.
3. Ссылку на раздел читай командой `node .agents/scripts/read-doc.mjs "docs/файл.md#раздел"`.
   Без `#раздел` команда покажет только оглавление. При недоступности команды найди заголовок
   через `rg -n '^#{1,6} ' <файл>` и прочитай диапазон до следующего равного/старшего заголовка.
4. Расширяй чтение при конкретном пробеле или зависимости. Когда найдены путь изменения,
   затронутые правила и проверки, переходи к работе. Отсутствие темы в карте не означает отсутствия правил.

Навигацию обновляй при смене путей/потока данных; само правило — только в его справочнике.
Код и миграции описывают текущую реализацию, продуктовые правила — требуемое поведение.
Расхождение между ними учитывай явно, а не объявляй автоматически нормой.

Общий источник навыков — `.agents/skills/{spec,implement,optimize,device}/SKILL.md`.
Загружай только нужный; в `.claude/skills/` — адаптеры к этим же файлам. Правила процесса
меняй в общем источнике. Порядок: решение человека → `AGENTS.md` → профильный документ/навык;
память и старые промпты — исторический контекст, не дополнительные обязательные проверки.
Уже прочитанный и доступный в контексте файл перечитывай при изменении или нехватке сведений.

## Продукт (кратко)

**Open** — мессенджер с публичной перепиской + соцсеть, растущая из неё. Любой чат может читать
каждый; посторонний оставляет реакцию/комментарий, но писать в чат может только участник. Лента
рекомендаций — из фрагментов переписки, постов и клипов. Звонок автоматически становится публичным
стримом. Это замысел продукта; готовность отдельных сценариев указана в карте и проверяется по коду.

## Рабочий процесс

- Одна сессия за раз, задачи последовательно; одна реализация, без параллельных веток/worktree
  (навык может поручить помощнику чтение или независимое ревью без изменения файлов).
- Новая задача — ветка от `master` (`feat|fix|chore/<коротко>`); в `master` не работаем. Продолжение
  начатой — в её ветке после `git status`/диффа/истории; посторонние правки не сбрасывать и не коммитить.
- Цикл: задача → ветка → сделать целиком (техрешения сам; вопросы — «Когда спрашивать») → проверки
  из раздела [команды и сборка](docs/development.md#команды-и-сборка) → человек проверяет на телефоне по чек-листу → правки в той же ветке →
  «мерджи» → `git merge --no-ff` и удалить ветку. Зелёные тесты — не разрешение на мердж.
- Полномочия (без спроса): пакеты (в т.ч. нативные), файлы конфигурации и `src/`, миграции и
  перегенерация `src/api/types.gen.ts`, сборки EAS/`adb install`/Metro, свои тестовые данные,
  коммиты/ветки/мердж после «ок». Заметные решения — в отчёт.
- Не может (нет доступа — попросить конкретно): дашборд Supabase, Google Cloud/Apple Developer,
  телефон в руках, публикация в сторы, пуш в `origin`.
- Коммиты — мелкие, Conventional Commits. Отчёт: что сделано, файлы, чек-лист для телефона,
  решения к перепроверке, что за доступом.
- Мердж — только после «мерджи» человека; push — по его просьбе.

## Когда спрашивать

Спрашивать (ответ знает только человек): сценарий, не описанный задачей; как выглядит; нужна ли
фича; какой из двух продуктовых вариантов; приоритет при делении на части. Не спрашивать:
библиотека/имена/структура/мемоизация/паттерн, ставить ли пакет или миграцию, «можно ли начинать».
Формат — выбор варианта, не проектирование; блокирует часть — сделай остальное.

## Чего не делать

- Мерджить в master без «ок» человека после проверки на телефоне.
- Создавать README/CHANGELOG и прочие документы без просьбы.
- Заглушки/моки в проде под видом фичи; не вышло — сказать прямо.
- Рефакторить за рамками задачи (заметил — в отчёт).
- При изменении кода прочитай разделы [Код](docs/development.md#код) и
  [Чего не делать в коде](docs/development.md#чего-не-делать-в-коде).

## Агенты и инструменты

Codex и Kimi Code читают этот файл напрямую; Claude Code — через `CLAUDE.md`.
Для изменения только инструкций/навыков проверяй формат, ссылки и дифф; сборка/тесты — при изменении
поведения приложения. Адаптеры, ссылки и покрытие карты: `node .agents/scripts/check-instructions.mjs`;
после изменения общих навыков обнови адаптеры той же командой с `--write` и повтори проверку.
Перед долгими командами прочитай [протокол ожидания](docs/development.md#ожидание-процессов).

Claude Code: общие навыки — через адаптеры `.claude/skills/`; вопросы — `AskUserQuestion`.
Для фоновых задач используй уведомления и результат того же task ID по общему протоколу.
`.claude/settings.json` задаёт разрешения Claude, не меняет общий процесс.

Codex: вопросы — `request_user_input_async` (`request_user_input` — только в поддерживаемом режиме),
иначе в чате; варианты короткие, рекомендуемый первым; пока ждёшь — делай независимую работу;
отсутствие ответа ≠ согласие. Фоновые команды — `exec_command` + `write_stdin` (проверяй код выхода);
фоновые процессы Windows через `Start-Process` — с `-WindowStyle Hidden`. В PowerShell после каждого
шага цепочки — `$LASTEXITCODE` (`&&` не везде). Скриншоты — `view_image`. `.claude/settings.json` в
Codex не переносится автоматически; sandbox не отключай ради совместимости.

Kimi Code: навыки — инструмент `Skill`; `.agents/skills/` читает напрямую (копии в
`.kimi-code/skills/` не создавай). Вопросы — `AskUserQuestion`. Фон — `Bash` с
`run_in_background=true`; в Windows — синтаксис Git Bash, прямые слэши. Скриншоты — `ReadMediaFile`.
`.claude/settings.json` не ослабляй ради совместимости.
