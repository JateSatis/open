# Как запускается Open на Android и iOS

Состояние проекта на 25 ноября 2026 года, после этапа 17, коммит `bac72e0` в `master`. Основной сценарий — холодный запуск установленного приложения с иконки, когда процесса Open ещё нет. Возврат из фона, открытие ссылки и смена аккаунта разобраны отдельно. Описание платформ опирается на конфигурацию проекта и локальные нативные проекты. Время первого видимого кадра измерялось на Android.

## 1. Весь запуск в одном месте

Для обычного запуска с сохранённым взрослым аккаунтом последовательность такая:

| Шаг | Что выполняется | Что видит пользователь |
| --- | --- | --- |
| 1 | ОС открывает нативное окно Open. Стартуют код приложения, Expo, React Native и среда выполнения Hermes. | Системная заставка Android или фон launch screen iOS. |
| 2 | Выполняется JS-точка входа. Open удерживает заставку, начинает журнал и регистрирует React-компонент `App` под именем `main`. | Заставка. |
| 3 | Первый рендер `App` получает `localAccountId === undefined` и возвращает `null`. Подписки запускают чтение каталога аккаунтов, наблюдение за сетью, состоянием устройства и входящими ссылками. | Заставка. Первое выполнение React уже состоялось. |
| 4 | Из каталога на устройстве выбран A. Open читает сохранённый слот A, создаёт его API-клиент, запускает восстановление SDK-сессии и публикует локальный выбор. | Заставка. Проверка токена может ещё выполняться. |
| 5 | `App` выбирает `QueryClient` для A. `AppRoutes` читает локальную дату рождения A. Если выбран основной интерфейс, монтируется вкладка «Чаты», которая может синхронно взять снимок списка из SQLite. | Под заставкой готовится конкретный экран. |
| 6 | Экран получил фокус, а его собственная обёртка получила `onLayout` с ненулевой шириной и высотой. Open один раз вызывает `hideAsync()`. | Появляется экран. При наличии снимка в первом кадре уже могут быть строки. |
| 7 | Основной интерфейс догружает данные по мере готовности сессии и сети. После скрытия заставки запускается предусмотренная для этого момента работа журнала и планируется прогрев JS-части LiveKit. | Экран уже доступен. Данные могут уточниться, в том числе с изменением маршрута. |

**Что удерживает заставку:** запуск нативной и JS-части, локальное определение выбранного владельца, локальное возрастное решение для выбранного аккаунта, построение и разметка активного экрана. Синхронная работа внутри первого рендера тоже входит в это время. Например, открытие SQLite при чтении сохранённого списка.

**Что может начаться до скрытия:** проверка связи, восстановление SDK-сессии, а при достаточно быстром ответе SDK — чтение настроек приватности, регистрация устройства, персональный Realtime и запросы экрана. У этих операций свои условия готовности. Ни ответ сервера, ни присоединение к каналу, ни получение свежего списка чатов не служат условием для `hideAsync()`. «Параллельно» здесь означает перекрытие по времени. Синхронные участки JS по-прежнему занимают общий JS-поток.

**Что специально отложено:** разрешение на отправку журнала после первого экрана и фоновая подготовка JS для звонков на основных вкладках. Вход пользователя в звонок может запросить ту же подготовку раньше фонового таймера. [Корень приложения](src/index.tsx) · [Маршрутизация и прогрев](src/navigation/routes/AppRoutes.tsx) · [Сигнал готовности экрана](src/navigation/routes/StartupScreenLayout.tsx)

## 2. От иконки до выполнения JavaScript

### Откуда берётся исполняемый код

Open использует Expo SDK 57, React Native 0.86 и Hermes. Поле `main` указывает на `./src/index.tsx`. Metro использует стандартную конфигурацию Expo для разрешения импортов и подготовки бандла. При сборке вместе с нативной частью поставляются JS-код для Hermes и ресурсы. Kotlin, Swift, нативные модули и платформенные представления работают в установленном бинарнике. Функции React, хуки, маршрутизация и бизнес-логика из TypeScript выполняются через JS-движок. Компиляция приложения не превращает каждый React-компонент в отдельный Kotlin- или Swift-класс. [package.json](package.json) · [metro.config.js](metro.config.js) · [Конфигурация приложения](app.json)

В release нативный загрузчик Expo Updates выбирает локально доступное совместимое обновление или встроенный бандл. В проекте задана политика runtime version по версии приложения. В локально сгенерированных Android Manifest и iOS Expo.plist указаны проверка обновлений при запуске `ALWAYS` и окно ожидания нового обновления `0` мс. Это позволяет начать с уже доступного кода. Выбор и чтение этого кода всё равно занимают время. В разработке источником JS может быть Metro. Поэтому изменения в рабочем дереве, содержимое установленного release и бандл, реально выбранный на телефоне, могут различаться. В замерах проекта записывают и сборку, и идентификатор обновления. [Конфигурация Expo](app.json) · [Профили сборок](eas.json) · [Пример проверки измеренной сборки](docs/android-cold-start-final.md)

## 3. Точка входа и первый рендер App

При выполнении [src/index.tsx](src/index.tsx) важны и импорты, и команды на уровне модуля. Импорт экрана делает его код частью графа приложения, а сам экран монтирует навигатор, когда выбирает маршрут. Стоимость разбора и выполнения затронутых модулей относится к старту JS. Для LiveKit в проекте предусмотрена отдельная отложенная загрузка.

1. `requestClient` зависит от модуля Supabase. При его выполнении читаются `EXPO_PUBLIC_SUPABASE_URL` и `EXPO_PUBLIC_SUPABASE_ANON_KEY`. Отсутствие любого значения вызывает ошибку ещё на этапе импорта. Создаётся исходный анонимный `AccountClient` без постоянного слота. Публичный ключ идентифицирует приложение при обращении к API. Личность и права пользователя для персонального запроса определяются его сессией. [Создание клиентов](src/api/supabase.ts) · [Получение токена операции](src/api/accountClient.ts)
2. `journalLaunchTime` фиксирует `Date.now()` во время загрузки JS-модуля. Это начало отсчёта журнала внутри приложения. Время нажатия на иконку фиксируется отдельно по видео. [Метка времени](src/features/recs/journal/launch.ts)
3. `bindHistoryReader` передаёт локальному слою истории функцию, которая вернёт текущий выбранный `user.id`. Сама привязка не читает базу. [Владелец локальной истории](src/features/chats/messages/local/reader.ts)
4. `preventAutoHideAsync()` удерживает нативную заставку. Вызов сделан на уровне модуля, до первого рендера. `setOptions({ duration: 0, fade: false })` убирает дополнительное затухание Expo на выходе. Затем `startJournalLifecycle(journalLaunchTime)` запускает подписки журнала, а `registerRootComponent(App)` регистрирует `main`. [Порядок вызовов](src/index.tsx)
5. На первом рендере `App` читает `useAuthBootstrap()`, номер выбора API и входящую ссылку. В исходном состоянии `localAccountId === undefined`, поэтому `App` возвращает `null`. Компонент уже смонтирован и его эффекты могут работать. Навигатор, экран входа и гостевой QueryClient на этом промежуточном шаге создавать не требуется. [Начальное состояние](src/features/auth/sessionState.ts) · [Хуки подписки на сессию](src/features/auth/useSession.ts)
6. В `useLayoutEffect` корень подписывается на смену владельца для очистки временного UI. Через `useEffect` запускаются монитор связи, наблюдение за устройством, восстановление сессии и Linking. Несколько потребителей `useAuthBootstrap` или `useSession` используют общий счётчик подписчиков и одно восстановление. Порядок получения асинхронных ответов между этими службами может меняться от запуска к запуску. [Корень](src/index.tsx) · [Подписки и восстановление](src/features/auth/sessionStore.ts)

## 4. Что именно Open восстанавливает с диска

У приложения есть три разных идентификатора. **`user.id`** выбирает аккаунт, его дату и локальные данные. **`session_id`** из JWT различает конкретные входы одного пользователя. **`requestSelection()`** — счётчик выбора API-клиента в этом JS-процессе. Он меняется при смене экземпляра клиента и используется ключом навигатора и защитой от запоздалых обработчиков. Обычное обновление токена в том же сеансе сохраняет этот ключ. [Владелец сессии](src/features/auth/sessionOwner.ts) · [Счётчик выбора](src/api/screenRequest.ts) · [Выбор клиента](src/api/supabase.ts)

### Каталог аккаунтов и миграция

1. Первый подписчик запускает `restoreAccounts()`. Повторные обращения разделяют один Promise. `readAccounts()` читает из AsyncStorage индекс по ключу `<legacySessionKey>:accounts`. В нём массив слотов и `selected` — выбранный `user.id` или `null`. У слота есть `userId`, ключ отдельной записи SDK и опциональные `sessionId` и email.
2. Если индекса ещё нет, Open проверяет старый ключ вида `sb-<идентификатор>-auth-token`. Валидная старая запись копируется в детерминированный слот с суффиксом `:session:legacy`, владелец становится выбранным. При чистой установке сохраняется пустой индекс. Наличие даже пустого индекса завершает миграцию и исключает повторное восстановление старого входа.
3. Если выбранный слот существует, `readSlotOwner` читает его сохранённую SDK-сессию. Проверяются непустые поля идентификатора пользователя и токенов, принадлежность записи слоту, извлекается идентификатор исходного сеанса. В этой ветке нет проверки `expires_at` как условия показа UI. SDK отдельно решает, нужно ли обновить токен.
4. `observe(selected)` создаёт `AccountSession` и его SDK-клиент с постоянным ключом конкретного слота. Слушатель `onAuthStateChange` и вызов `auth.getSession()` запускаются сразу, но `restoreAccounts` не ожидает их результата перед `publish()`. При холодном старте это делается для выбранного слота. Старые подписи остальных аккаунтов при необходимости дочитываются при открытии списка.
5. `publish()` выбирает API-клиент и записывает в Zustand `accounts`, `localAccountId`, `localSessionId`, `sdkStatus` и `session`. Теперь React может построить дерево нужного владельца. Очистка устаревших ключей `cleanAccountStorage` происходит после публикации. При ошибке восстановления первый подписчик повторяет попытку. Если обе попытки не удались, интерфейс переходит к входу.

AsyncStorage переживает завершение JS-процесса. Индекс и записи SDK имеют собственный срок жизни: переключение меняет выбранный слот, адресный выход удаляет слот, а очистка данных установки может убрать всё хранилище. QueryClient и черновики в памяти имеют другой срок жизни, см. раздел 9. [Формат и миграция хранилища](src/features/auth/accountStorage.ts) · [Порядок восстановления и публикации](src/features/auth/sessionStore.ts) · [Очереди изменений](src/features/auth/sessionChange.ts)

### Что означает результат SDK

| Состояние | Следствие для запуска |
| --- | --- |
| `localAccountId === undefined` | Локальный выбор ещё не известен. Корень ждёт, по умолчанию на экране системный splash. |
| `localAccountId === null` | Выбранного владельца нет. Доступна фаза `SignIn`, в том числе список других сохранённых аккаунтов, если они есть. |
| Есть ID, `sdkStatus === 'pending'` | Уже можно читать локальные данные этого аккаунта и выбирать экран. Персональные службы, которым нужна подтверждённая сессия, ждут. |
| `sdkStatus === 'session'` | SDK предоставил сессию, в том числе из своего кеша. Это разрешает работу служб выбранного владельца. Доступность сети измеряется отдельно. |
| `sdkStatus === 'offline'` | При сетевой ошибке без ответа SDK код пробует прочитать сохранённую сессию из слота. При наличии записи сохраняется локальный интерфейс. Персональная отправка, требующая подтверждения SDK, ждёт. |
| `sdkStatus === 'signedOut'` | После окончательного завершения сеанса Open публикует отсутствие выбранного владельца, если завершился выбранный сеанс, и удаляет соответствующий слот. Выбор другого сохранённого аккаунта остаётся явным действием. |

Первичный `INITIAL_SESSION(null)` сам по себе игнорируется: возможна временная ошибка обновления. Итог уточняет `getSession()` или последующее событие SDK. При действительной сессии, полученной из локального кеша, отдельного обязательного HTTP-обхода «проверить вход перед экраном» в Open нет. При отзыве или замене `session_id` старый клиент прекращает работу. Переходы `AppState` также управляют автообновлением токена. [Жизнь одного SDK-клиента](src/features/auth/accountSession.ts) · [Публикация выбранного состояния](src/features/auth/sessionStore.ts)

Когда экран действительно отправляет запрос, операция захватывает свой API-клиент. `AccountClient.accessToken` проверяет владельца до и после `auth.getSession()` и получает актуальный access token исходного сеанса. Обёртка `fetch` отбрасывает запрос завершённого клиента и проверяет идентификатор сеанса в пользовательском Bearer-токене перед транспортом. В параметрах клиента с постоянным слотом включены `persistSession` и `autoRefreshToken`; у временного клиента они выключены. Обычные запросы ограничены 9 с, Edge Functions — 20 с, загрузка файла в Storage — 10 минут. Эти сроки относятся к конкретным операциям. Таймаута «столько держать заставку, пока Supabase отвечает» в алгоритме скрытия нет. [Создание и транспорт клиента](src/api/supabase.ts) · [Проверка владельца](src/api/accountClient.ts) · [Сроки запросов](src/api/requestDeadline.ts)

## 5. Как React выбирает первый экран

После публикации локального выбора `App` получает `api = requestClient()` и `queryClient = accountQueryClient(api)`. Клиент запросов создаётся лениво для этого экземпляра API. У анонимного клиента свой кеш. Дальше дерево имеет следующую форму. [Корень](src/index.tsx) · [Владение QueryClient](src/features/auth/accountQueryClient.ts)

```text
App
└─ GestureHandlerRootView → KeyboardProvider → SafeAreaProvider
   └─ RequestClientContext.Provider → QueryClientProvider → HistoryReader.Provider
      ├─ ScrollTap → AppRoutes (key = номер выбора клиента)
      ├─ IncomingCallOverlay
      ├─ InAppMessageToast
      └─ ConfirmDialogHost
```

Внешние провайдеры нужны для жестов, клавиатуры и безопасных отступов. Внутренние передают согласованные API-клиент, кеш запросов и локального читателя. Оверлеи расположены над отдельными экранами и получают актуального владельца. Источники персональных событий и очередь подтверждений управляются отдельно. Компонента `AccountLayout` в этом дереве уже нет.

### Локальная дата и таблица маршрутов

`AppRoutes` использует `useBirthDateGate(localAccountId)`. Хук совмещает два независимых чтения. Первое получает локальную дату этого аккаунта для решения прямо сейчас. Второе, `useMyPrivacySettings`, получает настройки через API, когда известен пользователь SDK и запрос может выполниться. Чтение локальной даты идёт через запрос с `networkMode: 'always'`, `meta.localOnly` и `staleTime: Infinity`. Поэтому даже при остановленных сетевых запросах локальное чтение продолжает работать. [Связь двух источников](src/features/privacy/queries.ts) · [Параметры локального запроса](src/features/privacy/useLocalBirthDateDecision.ts)

| Что известно локально | Фаза навигации | Первый обычный экран |
| --- | --- | --- |
| Локальный выбор ещё читается, либо есть владелец, но его возрастное решение ещё загружается | `loading` | Навигатор ещё не рисует маршрут. При холодном запуске сохраняется splash. |
| Выбранного аккаунта нет | `SignIn` | Вход с доступными провайдерами и выбором сохранённых аккаунтов. Локальная дата гостю не требуется. |
| Есть владелец, даты нет, она невалидна или лежит в будущем | `BirthDate` | Форма «Дата рождения». Отправка доступна после получения SDK-сессии. |
| Валидная дата даёт возраст меньше 13 лет | `BirthDate` | Та же ветка навигации показывает ограничение «Регистрация в Open возможна с 13 лет». |
| Возраст 13 лет или старше, либо есть совместимая старая отметка допуска | `Tabs` | Основные вкладки. При открытии с иконки стартовая вкладка — `chats`. |

`readLocalBirthDate` одним `multiGet` читает `privacy.birthDate.<userId>` и прежний `privacy.birthDateKnown.<userId>`. Приоритет у самой даты. Значение `1` в старом ключе при отсутствии даты трактуется как допуск до уточнения сервером. Ошибка дискового чтения даёт результат «дата требуется». Код проверяет формат и реальность календарной даты. Границу дня для возраста считает как календарный день в UTC+14. После отправки формы ответ сервера имеет приоритет в кеше текущего сеанса на этот день. На диск сохраняется сама дата. [Правила вычисления возраста](src/features/privacy/localBirthDate.ts) · [Форма и экран ограничения](src/features/privacy/BirthDateScreen/index.tsx)

Если настройки сервера приносят дату, она обновляет локальный кеш и хранилище. Пустое поле `birthDate` в полученных настройках отзывает прежний допуск и может вернуть из «Чатов» к форме. Оно сохраняет ранее установленное ограничение «младше 13»: сервер не хранит отклонённую дату. Ответ прежнего владельца проверяется перед применением. При смене фазы `NavigationContainer key={phase}` создаёт стек соответствующей фазы. Эта смена ключа отдельна от смены аккаунта у `AppRoutes`. [Сверка с сервером](src/features/privacy/useLocalBirthDateDecision.ts) · [Выбор стека и вкладки](src/navigation/routes/AppRoutes.tsx)

### Если приложение открыли по ссылке

`useIncomingLink` живёт в `App`, выше навигатора. Он устанавливает обработчик `Linking` и асинхронно получает начальный URL. Таблица `destinationForURL` переводит поддержанный путь в маршрут, например `openger://chats/<chatId>`. Более свежая ссылка имеет приоритет над запоздавшим результатом `getInitialURL()`. Доставка ждёт готовности навигации и наличия маршрута в текущем стеке. Поэтому ссылка на чат может пережить вход или ввод даты. Она не даёт доступа к чату до разрешённой фазы. [Приём ссылки](src/navigation/useIncomingLink.ts) · [Таблица путей](src/navigation/links.ts)

У ожидающей ссылки хранится владелец. Полученная до определения аккаунта или во время гостевого входа ссылка может привязаться к следующему выбранному аккаунту. При смене уже известного владельца на другого такая ссылка отбрасывается. Успешный `take()` потребляет её один раз. Готовность самого навигатора и готовность разметки для скрытия splash — разные сигналы. Скрытие не ждёт завершения всех переходов по ссылке. [Доставка из AppRoutes](src/navigation/routes/AppRoutes.tsx)

## 6. Откуда берутся строки на первом экране «Чаты»

1. `ChatsScreen` читает локального владельца из `HistoryReader`. `useChats` обращается к QueryClient этого аккаунта с ключом `['chats']` и вызывает `routeOptions(reader, 'chats', ...)`. Один и тот же ключ у A и B безопасен, потому что экземпляры QueryClient различаются. [Экран](src/features/chats/ChatsScreen/index.tsx) · [Хук списка](src/features/chats/useChats.ts) · [Ключ запроса](src/features/chats/chatsKey.ts)
2. При создании запроса `initialData` синхронно читает последний снимок маршрута из SQLite по паре `(reader, 'chats')`. Первый вызов `localHistory()` открывает `open-history.db` в каталоге кеша установки и выполняет миграцию схемы. Далее используется тот же открытый экземпляр. В базе раздельно хранятся снимки маршрутов, куски переписки, место чтения и отметки прочтения. Система может освободить каталог кеша. Отсутствующий снимок — предусмотренный случай. [Инициализация запроса](src/features/chats/messages/local/route.ts) · [Открытие SQLite](src/features/chats/messages/local/database.ts) · [Схема](src/features/chats/messages/local/storage.ts)
3. При наличии снимка список получает данные сразу. `initialDataUpdatedAt: 0` позволяет обновить их с сервера. Если снимка нет, возможен экран с индикатором, а при приостановленном офлайн-запросе хук убирает индикатор. Сбой фонового обновления сам по себе не прячет уже показанные строки. Сохранённый непустой список, пустой список и доступный сетевой ответ — три разных состояния.
4. Сетевой `listChats(api)` получает ID пользователя, параллельно вызывает RPC `my_chat_list` и получает подписки. Затем читает карточки найденных чатов, участников и собирает упорядоченные строки. Снимок записывается обратно, только если сохранились выбранный клиент и локальный читатель. Свежий ответ обновляет принадлежащий аккаунту QueryClient. [Сборка серверного списка](src/api/chats.ts) · [Защита записи на диск](src/features/chats/messages/local/route.ts)
5. Экран отдельно запрашивает присутствие собеседников, приглашения и сводку «Сохранённых». Их результаты дополняют уже доступный интерфейс. История конкретной переписки открывается своим путём при входе в чат. Для показа вкладки приложение не восстанавливает заранее все переписки и вкладки. [Экран списка](src/features/chats/ChatsScreen/index.tsx) · [Открытие истории переписки](src/features/chats/ChatConversation/useHistoryOpening.ts)

Для других задач полезно искать вызовы `routeOptions`: тем же механизмом пользуются, например, карточка чата, канал и состояние подписки. Гарантии дискового кеша нужно проверять у конкретного хука. Наличие данных в React Query одного процесса само по себе не обеспечивает их наличие после перезапуска.

## 7. Что означает «первый кадр» и когда уходит splash

| Сигнал | Что действительно произошло |
| --- | --- |
| React выполнил `App()` | Сработал JS-код корневого компонента. Результат может быть `null`. |
| `NavigationContainer.onReady` | Навигатор готов принимать доступные ему переходы. Open фиксирует маршрут для журнала и пробует доставить ссылку. |
| `StartupScreenLayout` сообщает готовность | Конкретная обёртка экрана в фокусе и получила от нативной разметки ширину и высоту больше нуля. Для основных вкладок проверяется экран вкладки. Внешний маршрут `Tabs` пропускается. |
| Завершился `SplashScreen.hideAsync()` | Open разрешил раскрыть интерфейс, уведомил журнал и установил `splashHidden`. Модульный Promise `hideSplash` разделяется всеми маршрутами, поэтому нативный вызов один на этот запуск JS. |
| В видеозаписи виден экран или читается контрольная строка | Это две отдельные пользовательские метрики. Их можно измерить по кадрам, учитывая работу нативного рендера и дисплея после выполнения JS. |

В `StartupScreenLayout` событие `onLayout` сохраняет признак положительного размера, а эффект проверяет его вместе с `useIsFocused()`. Условия могут стать истинными в любом порядке. Отсутствие соединения, разрешения на микрофон, аватарки или результата запроса списка не мешает готовности разметки. Если позже с сервера придёт другая дата, пользователь выйдет или переключит аккаунт, навигация может построиться заново. Уже скрытая нативная заставка при этом не возвращается. У монитора есть три состояния. Системное отсутствие сети даёт `offline`. Успешный HTTP или живой сокет дают `online`; наличие сети без подтверждённой доступности сервера — `connecting`. Монитор проверяет состояние раз в секунду в активном приложении. Без сокета в спокойном состоянии пробы прореживаются до каждого шестого тика, таймаут отдельной health-пробы — 5 с. Health-запрос, получение SDK-сессии, серверный запрос экрана и присоединение к персональному каналу имеют разный смысл и разные моменты завершения. [Расчёт состояния](src/features/connection/connectionStore.ts) · [Общие сроки HTTP-операций](src/api/requestDeadline.ts)

Две детали важны при чтении стартовой трассы. Во-первых, у журнала есть собственное раннее наблюдение за аудиовыходом и типом сети для контекста событий. Вызов нативного аудиомодуля здесь не указывает на вход в звонок. Во-вторых, «фоновой» называют и короткую работу, которая всё ещё выполняется в JS: например, открытие локальной базы для очереди прочтений. Отсутствие прямого `await` в цепочке скрытия splash исключает обязательное ожидание ответа, но не конкуренцию за время выполнения. ### Что происходит с LiveKit после первого экрана

На основных вкладках `MainTabs` ждёт оба признака: свой layout и завершившееся скрытие splash. Затем планирует `requestAnimationFrame`, таймер на **1000 мс** и `requestIdleCallback(prepareLiveKit)`. Это даёт окну первого нажатия пройти до тяжёлой JS-подготовки. Реальный старт прогрева зависит от доступности JS и может произойти позже. При уходе с вкладок незапущенные обработчики отменяются. На экране входа и форме возраста фоновый таймер вкладок отсутствует. [Планирование](src/navigation/routes/AppRoutes.tsx)

`prepareLiveKit()` разделяет один Promise между фоновым вызовом и явным входом в звонок. Ленивый `require('./livekitSdk')` выполняет JS SDK из поставленного кода; сетевое скачивание библиотеки этим вызовом не предусмотрено. `loadLiveKit` вызывает `registerGlobals()` и при наличии нативных фоновых таймеров подключает их к `CriticalTimers`. При неудачной подготовке Promise сбрасывается для следующей попытки. Только действие входа/начала звонка проходит путь разрешений, получения токена, настройки аудио и подключения `Room.connect`. [Подготовка](src/features/streams/livekitGlobals.ts) · [Загрузка SDK](src/features/streams/livekitSdk.ts) · [Действие пользователя](src/features/streams/useJoinCall.ts) · [Аудио и комната](src/features/streams/callSession.ts)

## 9. Смена аккаунта, выход и возврат из фона

**Переключение A → B → A в живом процессе.** Список доступен через «Профиль → Аккаунт», даже если профиль ещё не загрузился. Выбор оставшегося аккаунта возможен с экрана входа, а другого аккаунта — с формы даты и экрана ограничения. `chooseSavedAccount` передаёт выбор в `selectAccount`. Тот проверяет слот, сохраняет выбор на диск, при необходимости создаёт его `AccountSession` и публикует состояние. Если идёт звонок, перед сменой появляется «Выйти из звонка и переключиться?». Отмена сохраняет и звонок, и владельца. [UI списка](src/features/auth/SavedAccounts.tsx) · [Подтверждение выбора](src/features/auth/accountChoice.ts) · [Хранилище выбора](src/features/auth/sessionStore.ts)

**Что пересоздаётся.** Новый API-клиент в качестве выбранного увеличивает `requestSelection`. Корень передаёт согласованные значения в контексты; `AppRoutes key={selection}` сбрасывает стек и локальные состояния экранов. Повторно применяются дата и маршрут B. При возврате в A живой экземпляр API снова получает прежний QueryClient A и собственные черновики. Глубоко открытый экран A при этом не восстанавливается. Обычный refresh токена того же сеанса сохраняет навигатор. Обработчики старого экрана проверяют номер выбора перед навигацией. [Корень](src/index.tsx) · [Хранилища на экземпляр клиента](src/features/auth/accountStore.ts) · [Защита навигации](src/navigation/index.ts)

**Что закрывается явно.** `startAccountPresentation` при смене владельца останавливает голосовое воспроизведение, выгружает недавний поиск из памяти, сбрасывает активный чат, подтверждения, уведомления и входящий звонок, завершает участие в текущем звонке, закрывает комментарии и выбор медиа. Ожидающие вопросы получают отрицательный ответ. Черновики и исходящие записи отделены по их API-клиенту. Персональный Realtime обслуживает выбранный аккаунт. Серверная операция, начатая A, может корректно завершиться для A, пока этот сеанс остаётся действительным. Новое состояние B защищено от запоздалых результатов A. [Очистка представления](src/features/auth/accountPresentation.ts) · [Регрессии владения запросами](src/api/accountOwnedRequests.test.tsx)

**Добавление и выход.** При входе через провайдера обмен ID-токена выполняет отдельный временный клиент. После успеха `addSession` сохраняет слот и делает его выбранным; отмена добавления сохраняет прежний выбор. Выход адресован конкретному аккаунту и исходному сеансу. При завершении `AccountSession.dispose()` помечает API-клиент завершённым, освобождает его ресурсы, закрывает подписки и каналы. Очистка QueryClient отменяет запросы и удаляет кеш. Повторный вход с тем же `user.id` и новым сеансом получает новый экземпляр. Выход из невыбранного A сохраняет B. После выхода из выбранного B оставшиеся аккаунты видны на экране входа для явного выбора. [Вход](src/features/auth/signIn.ts) · [Адресный выход](src/features/auth/signOut.ts) · [Освобождение ресурсов](src/features/auth/accountSession.ts) · [Очистка кеша](src/features/auth/accountQueryClient.ts)

| Где данные | Что переживают | Примеры |
| --- | --- | --- |
| AsyncStorage установки | Перезапуск процесса, пока соответствующая запись сохранена | Индекс и выбранный аккаунт, слоты SDK, дата по пользователю, сохранённая очередь журнала. |
| SQLite в каталоге кеша | Перезапуск, пока сохранена база | Снимок «Чатов» и других поддержанных маршрутов, куски истории и позиция чтения по владельцу, отложенные прочтения. |
| Память экземпляра API / QueryClient | Переключение на другой аккаунт и обратно в одном процессе в пределах срока жизни данных | Кеш запросов, персональные черновики, исходящие и оптимистичные изменения. Дисковое восстановление есть лишь там, где фича реализует его отдельно. |
| Дерево экранов и временный UI | Жизнь соответствующего дерева или представления | Стек, локальные `useState`, раскрытый диалог, активный чат, выбранные для текущего действия медиа. |

**Возврат из фона.** Пока процесс жив, корень и навигация продолжают существовать. Событие `AppState.active` пробуждает соответствующие службы: монитор проверяет связь, SDK возобновляет автообновление, проверяются устройство и входящий звонок, очередь прочтений получает возможность продолжиться. Журнал возобновляет отсчёт показа; при выполнении его условий после отсутствия дольше пяти минут заводится новая аналитическая сессия `resume`. Это не смена Supabase-сессии. Если ОС успела уничтожить процесс, следующий вход снова проходит холодное восстановление с диска, включая выбор аккаунта. ## 10. Что действительно измерено

Холодные запуски измерены по видеокадрам на realme RMX3840 с Android 16, по три запуска в каждом режиме. Финальная release-сборка содержит код `c319c50`. В обоих исследованиях начало интервала — первая видимая реакция иконки на нажатие после остановки процесса. Конец — первый различимый целевой экран и отдельно первая читаемая строка **Scroll benchmark chat**. В девяти финальных запусках с сохранённой сессией обе границы совпали.

| Условие | Этап 1, медиана до экрана | Этап 17, медиана до экрана | Изменение |
| --- | ---: | ---: | ---: |
| Чистая установка, Wi-Fi, форма входа | 2 191 мс | 3 744 мс | +1 553 мс |
| Сохранённая сессия, Wi-Fi, действительный токен | 1 505 мс | 1 422 мс | −83 мс |
| Та же сессия без сети, действительный токен | 1 453 мс | 1 338 мс | −115 мс |
| Та же сессия без сети, истёкший токен | 27 249 мс | 1 254 мс | −25 995 мс |

Самая большая разница наблюдалась там, где экран теперь может открыться с диска во время восстановления истёкшей сессии. Чистая установка в этой серии оказалась медленнее. Замеры охватывают изменения всего цикла и дают время от иконки до результата на одном устройстве. Для определения стоимости отдельного импорта, миграции SQLite или чтения AsyncStorage нужны дополнительные измерения соответствующего участка. В отчётах приведены диапазоны, исходные прогоны, условия сети и сборки. Цифр для iOS эта серия не даёт.
